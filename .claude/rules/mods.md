# Mods

Rules for mods in this marketplace. They sit beside CLAUDE.md: everything there (README,
readme.md table, marketplace.json, comments, versioning) applies to mods too, except where
this file says otherwise.

Primary reference: [Getting started with Claude Code mods](https://claude.dev/blog/getting-started-with-claude-code-mods/).
When this file and the guide disagree, the guide wins and this file is updated.

Reference implementation: [`plugins/token-weather`](../../plugins/token-weather/README.md).

## What a mod is

A mod is a normal plugin whose behaviour lives in a hooks module: `hooks/hooks.json` names a
TypeScript (or JavaScript) module instead of shell commands, and the module exports one
`register(on, options)` that hooks session events as functions `($, e, next)`. A plugin can
also carry skills, agents or commands beside its module; each component is held to its own
rules.

A plugin is a **mod** for the purposes of review and the checks when its `hooks/hooks.json` has a
`"modules"` key.

## Layout

```
plugins/<name>/
  .claude-plugin/plugin.json   — manifest; "types": "./types/index.d.ts" when the module uses $.state
  .claude-plugin/types/        — generated by Claude Code on load; git-ignored, never committed
  hooks/hooks.json             — { "modules": ["./register.tsx"] }
  hooks/register.tsx           — the hooks module (.ts, .tsx, .js or .mjs)
  types/index.d.ts             — PluginState contract for every $.state key the module uses
  tests/*.test.ts(x)           — run by `claude plugin test`
  tsconfig.json                — optional: { "extends": "./.claude-plugin/types/tsconfig.json" }
  README.md
```

## Authoring

Write the mod the way the guide describes: ask Claude Code for it, and the built-in
plugin-authoring skill writes it and offers to hot-reload it in the session. Mods do not go
through `/plugin-dev:create-plugin`; that workflow audits skills, agents, commands and command
hooks, and does not understand hooks modules.

To try a branch's mod from this repo, use the throwaway marketplace in CLAUDE.md's Workflow
section, or `claude --plugin-dir plugins/<name>` for one session.

## Checks

There is no CI. Run these three commands locally before merging a change to a mod; all must pass:

```
claude plugin validate plugins/<name>
claude plugin test plugins/<name>
python3 scripts/check_plugins.py
```

- `claude plugin validate` must pass. It also prints what the module hooks and calls, which
  is what the Capabilities check reads.
- Tests are expected, not required: a mod with no tests passes `check_plugins.py` with a notice. Any test that
  exists must pass. Cover the behaviour the mod exists for; for a mod that draws, mount the
  drawing through the engine (`$.ui.mount`), as token-weather's `tests/band.test.tsx` does.
  That is the test that catches a module that throws while drawing.
- Type-checking (`npx tsc -p plugins/<name>`) is optional. It needs the types Claude Code
  writes into `.claude-plugin/types/` when it loads the mod, so it works only after the
  mod has been loaded once on that machine.

## README

On top of CLAUDE.md's installation and usage requirements, a mod's README must have:

- **Built against**: the Claude Code version the mod was built and tested on
  (`claude --version`). The mod API can change between releases; this line makes a break
  traceable.
- **`## Capabilities`**: what the module can reach beyond drawing and its own state. Name each
  of `$.process`, `$.fs`, `$.http` and `$.env` the module calls, and what it uses it for. A
  mod that calls none of them says so in a sentence. `check_plugins.py` fails a mod that calls one of these
  without naming it here. A mod runs with the same access Claude Code has on the machine it
  is installed on, so this is what to read before installing it.

## Versioning

Mods start at `1.0.0` and follow semver, like every plugin here.

## Writing the module

- Keep values that must survive a hot reload in `$.state` (declared in `types/index.d.ts`) or
  `$.store`. A reload runs `register` again, so the module's own variables start over.
- Never name a local variable `h` in a module that draws. JSX compiles to calls to a global
  `h`, and a local of that name shadows it: the render hook throws `h is not a function`.
- CLAUDE.md's comment rules apply to TypeScript: a file-header docstring and `/** */`
  docstrings, no inline comments.
